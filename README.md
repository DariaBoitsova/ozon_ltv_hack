# Прогнозирование LTV покупателей Ozon

Проект прогнозирования 30-дневной ценности покупателей на основе 30,6 млн
дневных записей об активности 250 000 пользователей маркетплейса. Изначальное
соревновательное решение преобразовано в воспроизводимый ML-pipeline с
point-in-time генерацией признаков, временной валидацией, обучением под целевую
метрику, сжатыми артефактами и консервативным ансамблированием моделей.

## Результат

- Public leaderboard RMSLE: **1,65408**.
- Официальный baseline по предыдущим 30 дням: **2,21618** среднего RMSLE на
  frozen folds.
- Средний RMSLE LightGBM на четырёх временных фолдах: **1,73347**.
- 256 сгенерированных признаков сокращены до 168 неповторяющихся модельных
  признаков.
- 15 обучающих срезов и один тестовый срез сохранены в виде пяти Zstandard
  Parquet-батчей по 50 000 пользователей на каждый anchor.

Public score и локальный time-CV намеренно указаны отдельно. Более поздние
rank-преобразования и post-hoc calibration улучшали некоторые локальные
диагностики, но ухудшали leaderboard score. Поэтому они сохранены в отчёте как
отрицательные эксперименты, а не представлены как улучшения.

## Основные особенности проекта

Target является прерывистым и содержит много нулей: отсутствие недавней
активности не означает нулевую будущую выручку. Поэтому основная сложность
заключается не только в выборе алгоритма, но и в корректной временной постановке
задачи:

1. Признаки используют события только до anchor date включительно.
2. Target равен GMV за период от `anchor + 1` до `anchor + 30` включительно.
3. Обучающий срез допускается в validation fold, только если его target window
   полностью закончился до начала доступной истории validation-среза.
4. Каждый срез содержит точное множество из 250 000 пользователей, включая
   пользователей без истории.

## Группы признаков

- суммы активности за 7/14/30/60/90/180 дней и всю историю;
- количество активных дней, дней с поиском, корзиной, заказом и покупкой;
- статистики положительного GMV и доля неактивных дней;
- давность активности, поиска, корзины, заказа и покупки;
- интервалы между покупками и exponentially decayed occurrence/amount signals;
- тренды текущих и предыдущих периодов длиной 7/14/30 дней;
- funnel-признаки и доли Search/Catalog со сглаживанием `+1`;
- cohort, tenure и глобальные месячные сигналы активности рынка.

Точные равенства между каналами и монотонные дубликаты raw/log исключены из
модельной матрицы. `user_id`, порядок строки и anchor date используются только
как метаданные и никогда не передаются модели.

## Структура проекта

```text
ozon_ltv_forecasting/
├── src/ozon_ltv/              # признаки, данные, модели, метрики и ансамбли
├── pipelines/                 # исполняемые CPU/GPU pipelines
├── notebooks/                 # компактный обзор проекта
├── tests/                     # синтетические тесты утечек и контрактов
├── configs/                   # зафиксированные конфигурации экспериментов
├── docs/                      # архитектура, результаты и пункты для резюме
├── data/README.md             # контракт внешних данных
└── artifacts/README.md        # контракт генерируемых результатов
```

Соревновательные данные и тяжёлый Parquet-кэш не дублируются внутри
портфолио-папки. Корень исходного репозитория передаётся pipelines через
`--project-root`.

## Воспроизведение результата

Находясь в этой папке и используя Python 3.11+:

```powershell
python -m pip install numpy pandas polars pyarrow lightgbm scikit-learn pytest
python -m pytest tests -q
python pipelines/build_features.py --project-root ../..
python pipelines/validate_lightgbm.py --project-root ../.. --threads 4
python pipelines/train_champion.py --project-root ../.. --threads 4 --iterations 965
```

Сохранённый champion удалось точно воспроизвести только на четырёх потоках
LightGBM: `log-correlation = 1,0`, средняя абсолютная разница в log-space —
`1,56e-17`. Запуск на 14 потоках был быстрее, но дал небольшое численное
отличие, поэтому воспроизводимые команды по умолчанию используют четыре потока.

Для валидации модели на NVIDIA GPU:

```powershell
python -m pip install "xgboost>=2.1,<4"
python pipelines/validate_xgboost_gpu.py --project-root ../..
```

GPU-кандидат сравнивается с LightGBM только на общих keyed OOF-строках:

```powershell
python pipelines/analyze_diversity.py `
  --control-oof artifacts/lgbm_oof/oof_lightgbm.parquet `
  --candidate-oof artifacts/xgb_oof/oof_xgboost.parquet `
  --output artifacts/xgb_oof/diversity_gate.json
```

## Контроль качества

- синтетический off-by-one тест границ features и target;
- проверка точного множества пользователей, исходного порядка и одной строки
  на пользователя;
- проверки null, infinity и отрицательного target;
- хранение признаков в `float32` и потоковое чтение Parquet;
- атомарные и возобновляемые OOF checkpoints;
- отдельные метрики для zero-target и positive-target сегментов;
- неотрицательные веса log-space ансамбля, подобранные на общей OOF-матрице;
- SHA-256 manifests и строгая проверка submission contract.
